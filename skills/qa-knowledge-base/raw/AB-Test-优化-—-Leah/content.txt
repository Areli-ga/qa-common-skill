需求1：从事件分流到用户属性分流
1.1 神策公共属性注入
核心思路：在自研 AB 系统返回分组结果的那一刻，立即调用神策的 registerSuperProperties，（h5是 registerPage）把实验分组写入公共属性。之后该用户触发的所有神策事件，都会自动携带这个字段，无需每个事件单独传。

需求 2  现有后台增加 Layer （实验层）字段

为什么需要 Layer:
现有 Feature 列表越来越多(截图中已有 10+ 个),缺乏业务分类

Layer 之间规则说明：
同 Layer 内的 Feature 默认互斥，同时生效会互相干扰。
不同 Layer 的 Feature 默认正交，多个 Feature 业务上不相关，用户可以同时命中，独立分流、独立分析、可交叉对比。
所以针对多实验的情况：可以同时命中的实验可以放在不同的 Layer 同时测，比如新用户流程和奖励中心。但是同一个 Layer 的实验，最好只同时存在一个。

操作

说明



调整流量比例


改变分支的百分比


在 Rules 弹窗直接修改各 variant 比例

后端处理:
已分组用户: 保留原分组身份
新进入用户: 按新比例分配

增加新分支


在AB实验中增加新的分支


PM 操作: 
  1. 在 Variants 列表点击"+ 添加新分支"
  2. 填写 variant 标识(如 treatment_v3)
  3. 调整各 variant 比例,保证总和 = 100%

后端处理:
  - 已分组用户: 保留原标签(不会被切到新分支)
  - 新进入用户: 按新比例分到所有实验分支
注：首次未命中用户，再调整分支后，有可能会再次分组。
  
数据上的表现:
  - 新分支从加入时间点开始累积数据
  - 早期数据较少,PM 分析时需考虑时间维度

关闭某个分支(比例调到 0%)
删除分支保持一致

比例归 0,但保留已分组用户

在 Rules 弹窗把某个 variant 的比例改为 0%

后端处理:
  - 已命中该 variant 的用户: 保持原分组,功能继续生效
  - 新进入用户: 不再分到该 variant
  - 其他 variants 按相对比例分配(比例为 0 的不参与新分配)

数据上的表现:
  - 该 variant 的用户数停止增长
  - 已有用户的事件继续上报,可观察长期行为
  - 历史数据完整保留

适用场景:
  - 灰度收尾期(不想再新增,但保留观察老用户)
  - 实验已分出胜负,想看胜出分支的长期表现
  - 某个分支表现差,想停止新增但不影响老用户

关闭整个实验


实验下线,所有用户回到对照组


PM 操作: 在列表点击 Delete(沿用现有逻辑)

后端处理:
已命中 treatment_* 的用户: 功能回退,等同对照组
已命中 control 的用户: 不变(本来就是对照组)
整个 Feature 停止生效

神策侧:
abt_xxx 字段保留最后一次写入的值(保留历史数据,不删除)
神策档案里仍能看到该实验的历史数据
但不再有新事件归到 treatment 组

数据上的表现:
所有用户从此时起,行为表现等同 control 组
PM 可以继续查看实验历史数据
但实验已结束,不应再做新决策

适用场景:
实验完全失败,需要紧急回滚
实验结束,要把功能从 AB 切到全量



需求 4：分流调整，区分出未命中实验的用户
为什么做分流方式调整？
目前用户分组上，只有实验组和对照组，未命中实验的用户也会被算在对照组，

每个 Feature 的命中判定分为两层:


层级

决定者

作用

第一层 · 实验范围(Scope)


过滤规则(country / internalStaff / channel / registerTimeAfter)

哪些用户会被实验影响


第二层 · 分组规则(Variant)

百分比规则(percent_guest / percent_normal / time_range)

范围内用户分到哪一组

区分这两层是为了准确剔除未命中实验的用户,避免 control 组被污染。

variant 三态映射


variant 值

含义

判定逻辑

treatment

实验组

在实验范围内 + 命中百分比规则

control

对照组

在实验范围内 + 未命中百分比规则

not_in_experiment

未命中实验


不满足过滤规则,被排除在实验外

关键逻辑
1. 判定顺序(与现有规则引擎保持一致):

白名单 → 实验范围判定 → 百分比规则
   ↓           ↓              ↓
whitelist  / out_of_scope / rule

2. 返回范围:所有当前生效中的 Feature(包括 not_in_experiment 用户)
3. 性能要求:P95 < 100ms,用户级缓存 5-10 分钟


 
三、本次实验上线前后影响差异
3.1 整体改造的影响
字段从 abtestnewuser128 切换到 abt_{layer}_{标识},会产生以下影响:
影响 1 · 新老看板分离


数据范围

兼容性

处理方式

改造前的老 Feature 看板

字段不变,完全兼容

继续用老看板,不动

改造后的新 Feature 看板

使用新字段 abt_xxx

按新规范建看板

跨改造时间点的同一实验

不可直接对比

分两段分析:前用老看板,后用新看板

影响 2 · 历史数据无 abt_xxx 字段，无法直接使用分组来看
改造前的用户档案里没有 abt_xxx 字段
改造后第一次启动 App 才会被写入
跨改造时间点的趋势图会有数据断层，讨论如何处理
3.2 引入 not_in_experiment 的影响
影响 1 · PM 查数必须加过滤条件
改造完成后,PM 在神策做任何 AB 实验分析时:

分析步骤:
1. 创建分析(漏斗 / 留存 / 事件分析)
2. 不在事件上配 AB 过滤
3. 分组属性选择: abt_{feature_key}
4. 【必加过滤条件】: abt_{feature_key} 不包含 "not_in_experiment"
   ↑↑↑ 必须加!否则 control 组会被污染 ↑↑↑

→ 神策自动输出:
   treatment:layer:rule  → 实验组数据
   control:layer:rule    → 对照组数据
   (not_in_experiment 用户已被剔除)

为什么必须加:
不在实验范围内的用户行为与实验无关
不过滤的话会被错误算到 control 组
等价于神策原生 AB 测「只看命中实验的用户」的能力
影响 2 · 排除内部员工
如果想剔除白名单(内部员工测试)用户:

过滤条件: abt_{feature_key} 不包含 ":whitelist"
可与 not_in_experiment 过滤同时使用。

3.3 数据迁移策略
采用「双轨制 + 时间分界」,零迁移成本:
老实验继续用 abtestnewuser128 等老字段的看板assignments
新实验全部走新方案,PM 按新规范建看板
不做跨期对比:改造时间点是数据口径分界线
新看板强制规范:所有 abt_xxx 相关分析必须加 not_in_experiment 过滤
