# 01 · 一页纸 MVP(产品思维)

> 阶段:07 产品思维 · 状态:已定稿
> 解决 `读取产品文档 → 写测试用例` 的**前半段**:把飞书需求沉淀成可检索的知识库。

## 一页纸 MVP

| 格子 | 内容 |
|---|---|
| **用户** | 我自己——一名 QA(软件测试工程师) |
| **问题** | 写新需求的测试用例时:① 往期相关需求/功能散落飞书各处,**找不全**;② 历史功能逻辑久了就忘,新需求对老功能的影响漏判(**回归遗漏**);③ 需求里的 UI 状态图、字段表等关键信息,**回翻原文成本高** |
| **输入** | 飞书产品需求文档(wiki / docx),我手动丢链接进去 |
| **处理** | Claude 经 blocks 接口抓全文 + 表格 → 下载文档内图片 → 读图把 UI 状态/流程/字段表转文字 → 提炼**带「功能模块」的结构化摘要 + 结构化功能信息(逻辑/状态/边界/字段)** → 打标签 → 写 `related` 双向关联 → 更新索引 |
| **输出** | 一个本地知识库,写用例前用它:① 按功能模块/关键词**查到往期相关需求与历史逻辑**;② 问"这个模块历史上有哪些功能/边界/坑",得**跨文档综合回答**;③ 丢一篇新需求,给出"**相关往期功能清单明细 + 该重点回归的点明细**" |
| **不做什么** | 不直接生成测试用例、不上向量库/RAG、不上数据库、不做 Web 界面、不做多人协作、不做定时自动同步 |

## 范围补充(已达成共识)

- v1 **不纳入往期测试用例**,之后再加。
- v1 **不做编译层 / 往回织**(功能模块主题页),留 v2;但 v1 架构**预留位置**。
- MVP 终点是「答得出 / 查得到」,但"答"的内容必须对准写用例目的(相关历史功能、回归点),避免做成无目的的收藏夹。

## 验证方式(自用产品)

自己用 14 天看会不会扔。正向信号:写新用例时主动想先查它、查出来的相关历史确实减少了回归遗漏。
