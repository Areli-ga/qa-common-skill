Why

是什么 · 为什么

QA 写新需求的测试用例时,有三个反复出现的痛点:往期相关需求散在飞书几十个版本目录里、找不全;老功能逻辑时间一长就忘、容易漏测回归;需求里的 UI 状态图、字段表埋在图片/表格里,回翻成本高。

这个项目解决 读取产品文档 → 写测试用例 的前半段:把飞书需求文档沉淀成知识库。写用例本身是下一阶段。

核心理念:编译 > 检索。不在每次提问时现翻原始文档(RAG 式重复劳动),而是一次性把需求编译成结构化笔记 + 索引,之后直接读"炼好的成品"——又快又准,越用越厚。

Process

设计历程

先想清楚再动手——前三步不写一行代码,只产出"给 AI 看的"设计文档;实现后持续养库,最终封装成可日常调用的 skill。

Architecture

架构:进 · 存 · 取

脚本 = 机械活(快、稳、省 token)　Claude = 语义活(读懂、判断、读图)

进 · Ingest
飞书链接 → 加工流水线
脚本抓取正文 + 表格 + 下全部图 → raw/
Claude读图转文字 (UI 状态/流程/字段表)
Claude判断模块 + 提炼功能信息 (逻辑/状态/边界/字段)
脚本落笔记 notes/日期-模块-标题.md
脚本算关联 → 双向 related
脚本更新索引 INDEX.md
存 · 四层
纯文件,生 → 熟
raw/ 原料层 · 原文+表格+图,只读、永不改(事实来源)
notes/ 笔记层 · 每篇一份 Markdown,frontmatter + 摘要 + 功能信息
index/ 索引层 · INDEX.md,脚本生成、可一键重建
wiki/ 编译层 · 模块主题页,v2 预留(空)
取 · 检索
写用例前,4 条流
脚本模块/关键词检索 → 相关往期需求列表
Claude模块历史问答 → 跨篇综合演进/边界/坑
Claude新需求关联 + 回归点 → 现算"新 ✕ 历史"交叉
脚本按版本列需求 → 本次迭代要测啥
两条隐线　①往回织:每入一篇,旧笔记的 related 也回写指向它(关联级;编译级留 v2)。②架构算两条:能长大(分层留扩展口)+ 不会塌(原料只读、索引/笔记可由上层重建)。
Implementation

实现:脚本与分工

机械活固化成 4 个 Python 脚本(标准库、零第三方依赖、带详细日志);语义活由 Claude 按 SKILL.md 规则当场做。

脚本作用关键点
fetch.py抓取飞书文档:正文 + 表格 + 下全部图 + 版本判定超大图自动 sips 转 .read 副本(原图留底);原料层禁覆盖(--force);抓取/下图失败即非 0 退出;下图重试 3 次
relate.py关联打分,双向写 related同模块 或 共享功能标识符;排除通用词、神策埋点公参、通用内容事件;dry-run/--write;幂等
build_index.py扫 notes frontmatter → 重建 INDEX.md按 模块 → 版本 排序;derived、可一键重建
search.py检索:关键词 / 模块 / 版本关键词 · --module · --version,命中按相关度排序

机械 vs 语义 的分工铁律

  • 机械活归脚本:抓取、下图、关联打分、生成索引、检索——快、稳、可复跑、省 token。
  • 语义活归 Claude:读图、判断模块归属、提炼功能信息、跨篇综合、现算回归点——只有"会理解"的模型干得了。
  • 编排不写状态机:流程写在 SKILL.md 里当规则,Claude 读着执行。

Usage

使用方法

日常调用(新会话)

用自然语言即可触发 qa-knowledge-base;它会自动跳到项目、按本体规则执行。已打开的旧会话不一定会刷新新装 skill,必要时开新会话。

# 录入一篇(给「版本 + 飞书链接」)
把这篇飞书需求入库:V1.31.0 https://…/wiki/<token>

# 写用例前调研
写「奖励中心」用例前,帮我查往期相关需求 + 该重点回归的点

脚本命令(在项目目录内)

# ① 录入:抓取 → (读图/提炼) → 关联 → 索引
python3 scripts/fetch.py "<飞书链接>" <版本>
python3 scripts/relate.py --write
python3 scripts/build_index.py

# ② 检索三式
python3 scripts/search.py 宝箱
python3 scripts/search.py --module 奖励
python3 scripts/search.py --version V1.31
  • 版本来源:你给「版本 + 链接」时用你的(权威);没给才从文档提取,冲突标"待确认"。
  • 读图智能读:≤6 张全读;>6 张只读关键图;超大图读 .read 缩放副本。
  • fetch 调用纪律:输出大时不要接 | tail / | grep;重定向到文件再看。图多文档单独跑并给足 timeout。
  • 凭证:脚本自动从公司 config 拉取(需 VPN)。
Decisions

关键设计决策

01编译 > 检索

一次性编译成结构化笔记 + 索引,永久复用;不做 RAG 式每次现翻。

02纯文件化

状态全在磁盘,不依赖对话记忆——换会话零损失,这是文件化的回报。

03不上库

不上数据库 / 向量库 / RAG / 服务器。Markdown + 几个脚本,简单即稳定。

04分类只靠模块

taxonomy 边长(新功能新建一级、已有归二级);不设通用类型标签(通用词无区分度)。

05关联防误连

related 只看 同模块 或 共享功能标识符;排除通用词 + 埋点公参(level_number 等)。

06原料只读

raw 永不覆盖(事实来源);笔记/索引可由上层一键重建,错了能回退。

07边界克制

只收飞书需求文档;不直接生成测试用例——那是知识库建好后的下一阶段。

08关键词检索兜底

关联偶有漏连,但取③ 实测确认:关键词检索能把漏连的也拉出来,兜底成立。
