## 摘要
把「按用户特征圈人」这个此前**每个业务各写一段后端逻辑**的能力抽出来，做成**独立的用户标签系统**：后端统一定义和计算标签（分**实时**与 **T+1** 两种计算模式），把标签值记在用户身上，并提供一个 **Admin 共用的「目标人群选择器」组件**给**推送 / 任务 / 活动**三个系统复用 —— 业务侧只需在配置页新增一个「目标人群」字段、选条件看人数，**不再由后端为单个需求写取数逻辑**。标签清单分四类（账号与设备属性 / 学习状态 / 运营 / 行为与生命周期），实时标签由**业务方在状态变更时主动回调标签系统写入**，T+1 标签**每日 00:00 触发批量跑数**。选择器支持**包含区（全部条件 AND / 任一条件 OR）+ 排除区（组内固定 OR）**，**执行顺序恒为「先算包含，再减排除」**，运算符与值控件**由标签值类型自动决定**，并实时预估命中人数。关键设计：**业务侧存的是人群定义而非名单快照，标签每天更新、人群自动跟着变**。

## 功能信息（逻辑 / 状态 / 边界 / 字段）

### 基本信息与背景
- 产品 Owner：Aaron；优先级**中**；文档日期 2026-08-20；文档版本字段 v1.39.0（与用户给的一致）。
- 问题：**「按用户特征圈人」没有统一实现**，每个业务遇到这个需求时都是后端在该业务模块里单独写一段逻辑。
- 三个业务的典型诉求：
  - **推送系统**：对「近 7 天未活跃」推召回；对「完成 Unit 1 但未开始 Unit 2」推继续学习；**对「已关闭推送权限」的用户不发，避免无效发送**。
  - **任务系统**：给「新注册 7 天内」发新手任务；给「连续学习 3 天」发进阶任务；**A/B 实验：同一批新用户拆对照组 / 实验组，下发不同任务**。
  - **活动系统**：**九月绘本配音大赛只对中国、印尼两个地区展示入口**；面向「已参与但未提交作品」做二次提醒。
- 产品目标：**让「用户标签」成为各业务系统共同的、唯一的【目标人群】引用**。

### 需求范围（6 项）
| # | 模块 | 说明 |
|---|---|---|
| 1 | 标签定义管理 | 标签元数据：名称、ID、分类、值类型、数据源、计算规则、上下线状态、**计算模式（实时 / T+1）** |
| 2 | 实时标签计算 | 业务状态变更时触发标签值更新（如完成注册） |
| 3 | T+1 标签计算 | 每日批量跑复杂标签（如 7 日流失用户） |
| 4 | 标签存储与查询 | **用户 × 标签值**的存储；标签值记在用户身上，**支持按标签条件批量筛选用户** |
| 5 | **目标人群选择器组件** | Admin 共用组件，供三个业务系统复用 |
| 6 | 业务系统接入 | 推送 / 任务 / 活动各自增加「目标人群」配置字段 |

### 1. 计算模式判定标准
| 判断 | 计算模式 |
|---|---|
| 值由某个业务状态直接映射，且**状态变更点明确** | **实时** |
| 需要**跨时间窗聚合**（近 N 天、累计天数、连续天数） | **T+1** |
| 需要**关联多个数据源 / 多类事件**才能算出 | **T+1** |

### 3. T+1 标签清单（账号类型均为 `kid`）
| 标签 | 标签 ID | 值类型 | 口径 | 跑批说明 |
|---|---|---|---|---|
| 近 7 天活跃 | `active_7d` | 布尔 | — | 需按天扫描行为日志 |
| 近 30 天活跃天数 | `active_days_30d` | 数值 | 近 30 日中**有活跃行为的去重天数** | 逐天判断每天算不算活跃 |
| 连续学习天数 | `streak_days` | 数值 | **自昨日往前连续有学习行为的天数，中断即停** | **需序列扫描，中断判断不能增量算** |
| 首周活跃天数 | `first_week_days` | 数值 | **首次打开 App 后 7 日内的活跃天数** | 需回溯首次打开 App 后固定时间窗口 |
| **生命周期阶段** | `lifecycle_stage` | 枚举 | **未激活**：没有任何业务活跃行为；**活跃**：7 天内有业务活跃行为；**沉默**：14 天内没有业务活跃行为；**流失**：超过 14 天没有业务活跃行为 | — |
| 回流 | `is_returned` | 布尔 | **7 天内，用户的【生命周期阶段】从「流失」变为「活跃」** | — |

### 4. 标签列表页（Admin）
**页面职责：查看系统里有哪些标签可用，以及控制它们对业务方是否开放。**
| 元素 | 规则 |
|---|---|
| 搜索 | 对**标签名称或标签 ID 模糊匹配**，与三个下拉筛选**叠加生效**；**输入框回车等同点击搜索** |
| 筛选 · 分类 | 账号与设备属性 / 学习状态 / 运营 / **行为与生命周期** |
| 筛选 · 计算模式 | 实时 / T+1 |
| 筛选 · 状态 | 已启用 / 未启用 |
| 列表字段 | 标签名称、标签 ID、分类、值类型、计算模式、**更新触发点或跑批口径**、状态、最近更新时间 |
| 操作 | 已启用显示【禁用】，未启用显示【启用】，**点击即切换** |
| **禁用的影响边界** | **① 该标签立即从人群选择器中消失；② 已经在使用它的人群不受影响** |

### 5. 目标人群选择器（对业务侧的唯一引用组件）
> 「**业务方不需要理解标签怎么算出来，只需要选条件、看人数。**」
| 元素 | 规则 |
|---|---|
| 唤起方式 | 在**推送 / 任务 / 活动**的配置页点【选择目标人群】唤起，**三个系统复用同一份组件** |
| 条件关系 | 顶部切换 **【全部条件】/【任一条件】**，作用于「**包含**」整组条件；**切换后条件行之间的 AND / OR 标识同步变化并立即重新预估** |
| 包含区 | **至少一个条件**；**无条件时视为全站用户，需二次确认** |
| 排除区 | 可选；**排除组内部固定为 OR（命中任一即被排除）**；**执行顺序恒为「先算包含，再减排除」** |
| 标签下拉 | **只列出状态为已启用的标签** |

**四种值类型的运算符与控件（由标签值类型自动决定）**
| 值类型 | 运算符 | 值控件 | 示例 |
|---|---|---|---|
| 枚举 | **属于 / 不属于** | 多选面板（复选框） | 国家 属于 中国、印尼 |
| 数值 | **大于 / 小于 / 等于** | 数字输入框 | 已学单词数 大于 20 |
| 布尔 | **是 / 否** | **无值控件** | 推送权限已开启 是 |
| 日期 | **最近 N 天内** | 数字输入 + "天内" | 账号创建时间 最近 7 天内 |
| 日期 | **早于 / 晚于** | 单个日期选择器 | 圈某时间点前后的用户 |
| 日期 | **介于** | 两个日期选择器 | 圈某时间区间内的用户 |

**原型补充（img-02）**：右侧栏显示 **「预计命中 15,999，约占全站 1.2%（1,284,560）」+【重新预估】**；**「数据时效」**说明块会标出**当前条件是否全为实时标签**（示例写「全部条件均为实时标签，人群反映当前真实状态」）；每个条件行左侧带 **实时 / T+1 徽标**；底部主按钮 **【确认使用该人群】**；排除区空态显示「无排除条件」+【添加排除条件】。

### 6. 业务系统接入
- **三个系统的接入动作完全一致：在原有配置页增加一个「目标人群」字段**，点击唤起选择器（img-03 以推送系统「新建推送任务」为例：任务名称 / 推送文案 / **目标人群（必填，未选时显示「尚未选择目标人群」+【选择目标人群】按钮，标注「这就是本次需求给业务系统新增的唯一字段」）** / 发送时间）。
- 三系统用法：**推送** —— 创建推送任务时选人群，**发送前按人群拉名单**；**任务** —— 创建学习任务时选人群，**A/B 实验对照组、实验组各选一个**；**活动** —— 配置活动时选人群，**用户进入时判定是否展示入口**。
- **关键设计：业务侧存的是「人群定义」，不是名单快照 —— 标签每天更新，人群自动跟着变。**
- **⚠️ 原型明确提示：投放执行前要二次校验 —— 推送任务可能是三天前配的，执行时人群里引用的标签可能已下线或跑批失败。「创建可用 ≠ 执行时可用」。**

### 7. 计算与跑批
- **实时标签：由业务方在状态变更时主动回调标签系统写入。**
- **T+1 标签：每日 00:00 触发批量跑数。**

### ⚠️ 待确认（写用例前需拉齐）
1. **标签的账号维度 user vs kid 混用**：清单里 `country` / `push_enabled` 等是 **user**，`age_group` / 学习状态 / 生命周期是 **kid**。**一个 user 下多个 kid 时，「国家 属于中国 且 已学单词数 > 20」圈出来的到底是 user 还是 kid**、推送发给谁、活动入口按谁判定，全篇没定义 —— 这是最影响结果正确性的一条。
2. **T+1 跑批时区**：「每日 00:00 触发」按什么时区（服务器 / 用户本地）？产品是中国 + 印尼双区，跨时区会直接改变「近 7 天活跃」「连续学习天数」的结果。
3. **跑批失败的兜底**：原型自己提示了「执行时标签可能跑批失败」，但**失败后人群按什么处理**（用昨天的值、跳过本次投放、报警）没写；**二次校验失败后的产品行为**（中止 / 降级 / 通知）也没写。
4. **标签禁用与在用人群的矛盾**：规则写「禁用后已在使用它的人群不受影响」，但原型又提示「执行时标签可能已下线导致失败」。**已下线标签在执行时到底还算不算数**，两处说法要统一。
5. **预估人数的口径与时效**：预估是实时查询还是取 T+1 快照、**混合了实时与 T+1 标签的条件怎么预估**、预估与实际投放的人数差异是否可接受，都没写（只在原型里有「数据时效」提示块）。
6. **`ab_group_<实验名称>` 的枚举来源**：实验名称是自由拼接还是从 AB 平台同步；**实验下线后标签怎么处理**；与现有 AB 实验平台（`AB实验平台 / 实验分流机制`）的关系未说明 —— 存在同一分组两套真相的风险。
7. **生命周期阶段的定义有重叠**：「沉默：14 天内没有业务活跃行为」与「流失：超过 14 天没有业务活跃行为」在**第 14 天**这个点上同时成立，边界要精确到「≥ / >」。另「未激活」与「沉默」在**注册后从未活跃满 14 天**的用户上也会打架。
8. **「业务活跃行为」「活跃行为」「学习行为」三个词混用**，各自的事件口径没有定义清单 —— 直接影响 `active_7d` / `active_days_30d` / `streak_days` / `first_week_days` 四个标签的正确性。
9. **`country` 按打开 App 时的 IP 写入**：**VPN / 出国 / 换网络**会导致标签跳变；活动入口按 country 判定（九月绘本配音大赛就是这个场景）时，**用户在活动期间 country 变化的表现**没定义。
10. **正文清单缺 `family_type`**（原型里有），标签清单与实现清单需要对齐；反过来也要确认原型里没画的标签是否都要做。
11. **无条件 = 全站用户只做「二次确认」**：全站推送是高风险动作，是否需要权限控制、审批、人数上限保护，没写。
12. **没有埋点与权限章节**：谁能启用 / 禁用标签、人群定义是否有操作日志与变更记录，未定义；标签系统本身也没有可观测性（跑批成功率、标签覆盖率）的要求。
13. **人群定义是否可复用 / 可命名保存**：原型只有「确认使用该人群」，**三个业务重复配同一人群时能否引用同一份定义**、改了定义是否影响已在投放的任务，都没写。
