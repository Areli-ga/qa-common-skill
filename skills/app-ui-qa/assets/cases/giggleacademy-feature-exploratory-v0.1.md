# Giggle Academy 新功能探索性测试执行规范 v0.1

整理时间：2026-07-27

状态：新功能探索性测试的固定执行规范。此文件定义“读取原始用例 -> 转化执行文档 -> 用户准备首条用例场景 -> 正式用例与探索性验证 -> 单文件 HTML 报告 -> 沉淀 Git 资产”的完整流程。

本规范与核心主流程冒烟、Android 渠道包冒烟分开执行，不合并用例编号和结果统计。每次执行还必须读取当次生成的功能执行文档；不得只读本规范后根据页面自由探索。

## 一、输入要求

### 必须提供

- 新功能测试用例。支持 XMind、Excel、Markdown、图片、测试管理系统页面或网址。
- 功能名称、目标平台、App 版本 / build、服务器环境。新功能通常使用 QA 环境，若不是 QA 环境必须明确说明。
- 能执行第一条用例的 App 初始场景，以及需要的账号、数据、功能开关、灰度配置或特殊入口。
- 如果重启后功能入口较复杂，提供从 App 重启状态重新到达该功能的完整路径。

没有新功能测试用例时，不得开始设备操作，也不得用需求文档自行代替正式用例。

### 可选提供

- 需求文档、交互稿、设计稿、接口说明和已知风险。
- 历史缺陷、发布范围、明确不测项、允许或禁止的数据操作。

需求文档只用于补充理解和设计探索性检查，不能覆盖测试用例中明确写出的步骤与预期。需求与用例冲突时，先记录冲突并请使用者确认。

## 二、读取原始资料

先完整读取资料，再转化用例。不得一边读一边操作 App。

### XMind / 思维导图

- 读取完整层级、节点备注、附件和分支关系。
- 保留原节点路径或原始编号，记录无法识别、含义不明和依赖人工判断的节点。
- 图片型思维导图要记录纳入模块、排除模块和模糊节点，不凭猜测补全预期。

### Excel

- 读取所有与本功能有关的工作表、表头、合并单元格和备注。
- 保留原用例编号、前置条件、步骤、预期、优先级和平台范围。
- 空白预期或互相矛盾的单元格必须列为待确认项，不能自行编造。

### 网址

- 公开网址可使用普通浏览器读取。
- 需要登录态、公司账号、Cookie 或单点登录的网址，优先使用使用者已经登录的 Chrome，通过 Chrome 控制能力读取。
- 只有桌面界面、弹窗、下载或系统文件选择器才能完成的读取，使用 Computer Use 辅助。
- 读取过程保持只读。不得改写在线用例、提交表单、评论、发布或改变页面状态，除非使用者明确要求。
- 如果登录失效或权限不足，请使用者在原窗口完成鉴权；不得尝试绕过权限，也不要在尚未尝试已登录 Chrome 路径时要求使用者重复粘贴整份内容。

### 读取完成检查

- 列出所有原始资料来源和访问时间。
- 汇总原始用例数量、模块、原始编号、必测平台和无法读取的内容。
- 标出缺失前置条件、缺失预期、相互冲突和需要使用者确认的项目。

## 三、转化为功能执行文档

设备操作前，必须基于 `assets/feature-executions/feature-execution-template.md` 生成当次功能执行文档，并保存到：

```text
assets/feature-executions/<YYYY-MM-DD>-<feature-slug>-v0.1.md
```

功能执行文档至少包含：

1. 功能、版本、平台、服务器环境和资料来源。
2. 测试范围、不测范围、账号 / 数据 / 开关和安全边界。
3. 首条用例初始场景和重启后的重新进入路径。
4. 全局检查点、正式用例表、探索性检查表和来源追踪表。
5. 所有歧义、人工步骤、阻断依赖和报告关注点。

正式用例使用与主流程冒烟一致的表格结构：

| ID | 用例点 | 操作 | 预期 | 备注 |
| --- | --- | --- | --- | --- |

编号规则：

- 从原始测试用例转化的必测用例使用 `F01-01`、`F01-02`、`F02-01` 格式；第一段代表模块，第二段在模块内连续编号。
- 补充的探索性检查使用 `E01-01`、`E01-02` 格式，与正式用例分开统计。
- 保留原始用例编号或节点路径，并在来源追踪表中建立 `原始来源 -> 转化 ID` 映射。
- 不得静默删除、合并或改变原始预期。确需拆分时，一个原始用例可以映射到多个转化 ID；确需合并时必须写明原因并请使用者确认。

转化原则：

- 每个重要点击、滑动、拖拽、输入、页面进入、提交、成功态和返回动作单独成行。
- 在登录、权限、WebView / Unity / Flutter 切换、支付、分享、数据删除和服务端副作用等风险边界拆分步骤。
- 预期必须是可观察结果；无法从资料确认的预期标记为 `待使用者确认`。
- 语音、支付、真实分享、删除账号和生产侧写入默认设为人工或保护步骤，除非使用者明确授权并提供安全环境。
- 根据需求和原始用例添加有限、可解释的探索性检查，不得让探索项替代正式用例覆盖。

转化完成后先向使用者说明：

- 生成文件路径、正式用例数量、探索性检查数量。
- 未解决歧义和未读取内容。
- 执行所需环境、数据、入口及重启恢复路径。

在使用者确认 App 已准备到第一条用例可执行的场景后，才能开始设备操作。

## 四、执行前场景准备

新功能通常依赖 QA 环境、测试账号、服务端数据、功能开关或隐藏入口。至少确认：

- App 版本 / build 和目标服务器环境正确。
- 使用者已经完成无法由自动化安全准备的账号、数据、灰度、白名单和功能开关。
- App 当前停留在可执行第一条用例的位置；报告记录该初始场景由使用者准备。
- 已知如何从重启后的稳定页面重新进入功能。若路径复杂，必须由使用者提前写入功能执行文档。
- 明确禁止自动化执行的付款、发送、发布、删除、实名、隐私或生产副作用操作。

如果第一条用例场景尚未准备好，停止 App 操作并说明缺少的前置条件；不要从其它页面盲目寻找隐藏功能入口。

## 五、正式用例与探索性验证

1. 先执行 `F` 编号正式用例，确保原始用例完整覆盖；探索项不得挤占必测用例时间。
2. 每次操作前声明当前用例 ID，只执行当前行定义的动作。
3. 每个关键动作和检查点保存操作前后截图；异常、恢复和最终状态单独截图。
4. 以当前页面、需求、原始用例和历史风险为依据执行 `E` 编号探索项，范围限定在当前功能及其直接上下游。
5. 可优先观察边界值、空 / 错误 / 慢加载、重复点击、返回与重进、前后台切换、网络变化、权限、数据持久化、布局适配、状态一致性和错误恢复。
6. 不进行破坏性操作，不随意探索与功能无关的页面，不把猜测写成已确认缺陷。
7. 正式用例结果、确认缺陷、疑似风险、体验建议和自动化路线限制必须分开记录。

## 六、阻断与重启恢复

新功能验证遇到阻断时，不能因为单个流程中断而放弃所有后续覆盖：

1. 先截图并记录用例 ID、预期、实际、等待时间、已尝试动作和影响范围。
2. 在页面内进行 2～3 次安全、合理且有新截图确认的重试；不得重复使用过期坐标。
3. 多次尝试仍无法继续时，将当前用例标记为 `阻塞` 或 `自动化阻塞 / 需人工复核`。
4. 如果重启是安全且有恢复入口的，强制关闭并重启 App 一次，保存关闭、重启和恢复后的证据。
5. 按功能执行文档中的重启恢复路径重新进入，继续所有独立或仍可到达的后续用例。
6. 如果功能入口复杂且使用者没有提供重启后的进入方式，先请求补充路径，不得重启后盲目探索。
7. 重启恢复成功只证明流程可恢复；单次瞬态阻断不能直接判定为产品缺陷。只有稳定复现、崩溃或有诊断证据时才列为确认缺陷。

## 七、报告要求

最终必须生成：

- `report.md`：可编辑源报告。
- `report.html`：截图以 WebP data URI 优先内联的单文件报告；复制或上传时不依赖 `screenshots/`。
- `screenshots/`：原始证据。
- 可选 `logs/`：设备日志和脱敏诊断信息。

报告至少包含：

1. 功能、build、平台、设备、服务器环境和执行时间。
2. 原始用例来源、可选需求来源和转化后功能执行文档路径。
3. 使用者准备的首条用例场景、账号 / 数据 / 开关和重启恢复入口。
4. `F` 正式用例结果表和 `E` 探索性覆盖结果表。
5. 完整操作路径截图、阻断重试与重启恢复证据。
6. 确认缺陷：预期 / 实际、严重程度、复现率、证据和影响。
7. 可能风险：尚未充分证实但值得跟进的异常信号。
8. 建议点：体验、可测性、监控、日志、文案或交互改进建议。
9. 未执行、不适用、人工复核和因前置条件缺失而阻塞的内容。

正式用例通过率与探索性发现分开统计，不用探索项数量稀释正式用例失败或阻塞。

## 八、执行文档资产沉淀

- 每次生成的功能执行文档都保存到 `assets/feature-executions/`，并在 `INDEX.md` 登记。
- 不覆盖已经执行过的版本；需求或用例变化时增加版本号并保留来源与变更说明。
- 执行结束后提醒使用者检查并把功能执行文档提交到 `qa-common-skill` 的 Git 仓库。
- 新功能用例不会自动并入主流程冒烟。经过多轮验证、稳定且适合发布门禁的检查点，可在单独评审后抽象到 `giggleacademy-main-smoke-v0.1.md` 及其 JSON。
- 不提交账号密码、token、客户数据、内部 Cookie、运行截图或设备日志到公共用例资产目录。
