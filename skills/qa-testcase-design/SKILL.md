# 测试用例设计引擎

把「本次需求 + 覆盖清单 + qa-knowledge-base 历史知识」编译成全面、按风险排序、可执行的结构化用例，并发布为飞书评审文档。四支柱：保真读取、历史编译、逐维防漏、方法出例。

## 边界

- 不编造产品逻辑 / 接口字段 / AB 策略 / 视觉标准；缺信息写「待确认」，汇总进「风险与待确认」。
- qa-knowledge-base **只读**：不 ingest、不回写、不迁移；历史与 PRD 冲突进待确认，不覆盖 PRD。
- 飞书只**新建** docx：不改原 PRD、不覆盖历史文档。
- 不做：用例管理、执行报告、自动化脚本、反馈回流。
- **完成门槛**：除非用户明确要求「只本地输出」，发布到用户当次指定目录（未指定用默认目录）并拿到飞书链接才算完成；发布失败只算阻塞。

## 文件地图（按步骤读，不提前读）

| 何时 | 读什么 |
|---|---|
| 步 1、8 | `references/output-files.md`：交付目录结构、校验命令、失败修法 |
| 步 3 历史代理 | `references/history-kb-contract.md` |
| 步 6 一次读完，覆盖步 6-7 | `references/authoring-core.md`（**唯一规则源**：覆盖维度 / 测试设计方法 / 6 块骨架与机器校验硬规则） |
| 步 6 按端命中才读 | `references/code-risk-{backend,unity,native,h5}.md` |
| 步 8 发布 | `references/lark-output.md` |

脚本均在 skill 目录下 `scripts/`：`read_doc.py`、`kb.py`、`md_to_mindmap.py`、`validate_output.py`、`publish_to_lark_doc.py`。

## 工作流（8 步）

**1 进** — 接收飞书链接 / 粘贴文本，可选：改动点、影响端、提测说明、配置/AB 范围、目标飞书目录。先建交付目录 `D=/tmp/qa-testcase-design-<短名>-<YYYYMMDD-HHMM>/`，所有产物落这里。

**2 保真读取** — 飞书链接：
```bash
python3 scripts/read_doc.py "<飞书链接>" --out $D/source --quiet [--resume] [--allow-partial]
```
- 中断（图多/网络慢/被杀）用同一目录加 `--resume` 续跑，只补缺。
- 图片下载失败默认中止；用户接受部分读取才加 `--allow-partial`（只放宽图片，正文/凭证失败仍中止）。
- 脚本报「未解析内容块」或内嵌表读取失败 → 登记进「风险与待确认」，不静默忽略。
- SVG 图：脚本自动抽出内嵌位图，按图片清单里的「读」路径读；清单标 ⚠️ 的纯矢量 SVG 读不了，登记进「风险与待确认」。
- 粘贴文本：跳过读图代理，标「未读取图片/表格原始结构」风险。

**3 并行装载** — 在**同一条消息**里并行派出两个只读子代理（仅当图 ≤6 张且需求简单时可主线串行，产物不能少）；主线不等待，直接做步 4：
- **读图代理**：读 `$D/source/images/` 全部图 + `content.txt` 的【图NN】占位，逐图转录图内全部文案原文、字段名、数值/阈值、状态、按钮、流程走向、异常/空态，写 `$D/images-notes.md`（每图一节 `【图NN｜文件名】` + 转录 + 一行「本图对用例的信号」）。>8 张拆 2-3 个代理分片（每片 ≤6 张，写 `images-notes-<分片>.md`，主线合并）。每图一次通读，仅超宽/文字密集图允许至多一轮局部放大；竞品图/装饰图略读但登记原因；看不清写「不清晰待人工复核」；禁止推断图里没画的逻辑。
- **历史代理**：按 `history-kb-contract.md` 全文执行，写 `$D/history-hits.md`。**只给它交付目录路径**，由它自己读 `content.txt` + `tables.md` 提检索词（主线转述会让检索跑偏）。检索入口 `python3 scripts/kb.py <关键词> | --module <模块> | --version <版本>`；`kb.py` 找不到知识库时写一行判定为 `未读` 的数据行（理由写原因）并继续。

**4 对齐** — 主线用自己的话复述需求（目标/入口/路径/状态/端/接口/AB/配置/埋点/验收口径），列待确认项。**必须读 `tables.md`**：分支表→状态迁移、数值表→边界值、多条件表→判定表。同时把 PRD 业务规则逐条编号，写成需求理解末尾的 `### 业务规则追溯` 表（`编号 | 规则 | 来源 | 落点`，编号 R01 起，来源必填：正文段落 / 表N / 图NN；落点步 7 回填）。一条规则 = 一个可验证的业务约定（条件→结果、状态迁移、阈值、配置口径、埋点触发），分支表按行拆。待确认项按 authoring-core §C 分级：影响 P0 主链路、接口/配置/AB 发版口径、测试环境前置，或历史与 PRD 目标相反的是 `阻断`，**立刻停下问用户**，答复后标 `已确认` 并在问题列写「用户确认：…」；其余标 `记录` 写入待确认继续。

**5 合流验收**（出例前必须完成）—
- `images-notes.md` 每张图都有自己的 `【图NN｜文件名】` 节（略读也要一节写原因）；**P0 主链路判定依赖的关键图，主线亲自读原图复核**；图里出现、正文没有的规则补进业务规则追溯表（来源写图NN）。
- `history-hits.md` 含四类检索词组；抽查 1-2 条保留/丢弃判定合理，保留项已深读 notes。
- 两个代理产出里出现的阻断级冲突（读图与正文矛盾、历史与 PRD 冲突且影响 P0 / 配置口径）此时一次性汇总问用户，不拖到出例后。
- 任一代理失败/超时/验收不过 → 主线串行补做；**不允许缺着产物出例**。

**6 立场与防漏** — 读一次 `authoring-core.md`。先写风险判断（本次最该测什么，一句点题 + 3-5 要点），它决定 P0 排序。再按 §A 逐维过闸，每维只能「已覆盖 / N/A / 待确认」；按端范围读对应风险库，不涉及的端标 N/A。手册读取失败就停下提示用户，不凭记忆编维度。

**7 出例** — 按 authoring-core §C 写 `$D/testcases.md`：
- **先树后例**：第 3 块先落分解树，用例只挂叶层。第一层按端分（同时涉及 Admin 和 App 就先分 `### Admin`、`### App`），往下按「页面/模块 → 功能区 → 条件/状态」逐层细化，层数不设上限；数值逐项、分支逐行、结局逐个成节点。
- **节点用测试者视角命名**：页面名、控件/字段名、真实数据，不用 PRD 表号、规则编号、概念词；从根读到叶子就是一句完整测试步骤。跨端用例挂在看结果的一端，另一端操作写成前置节点。
- **一例一断言**，写成 `[P1-01] 操作或条件｜期望：结果` 两段短句；共用前置写成树标题，不写进叶子；每个功能点先按 §B 决策表选 1-2 个方法再出例。
- 六块标题逐字一致；用例行放 ` ```text ` 块、行首直接 `[P0-01]`；历史线索全部落到用例/风险/待确认/自检表。
- **回填追溯表落点**：每条规则写对应用例 ID，或「风险与待确认」里的 Q 编号；落点为空说明这条规则漏测，补用例或写 Q 项。

**8 校验与发布**
```bash
python3 scripts/md_to_mindmap.py $D/testcases.md $D/mindmap.puml
python3 scripts/validate_output.py --dir $D
python3 scripts/publish_to_lark_doc.py $D [--target "<用户指定目录>"]
```
- 校验 FAIL 先按 `output-files.md` 修法表回修文件；WARN 逐条处理（数值遗漏补用例或写进待确认）。
- 因 `阻断` 级待确认 FAIL 时，把这些 Q 项问用户；**不得自行改成已确认，也不得降级为记录**。
- 导图由脚本确定性生成，**不手抄 PlantUML**；用户只要主结构时加 `--compact`。同一条命令会在 `mindmap.puml` 旁边写出结构相同的 `mindmap.xmind`（XMind 8 格式，只存本地、不发飞书）。
- 发布失败：报告 `stage / code / msg`、本地目录与下一步；append 中断用 `--resume` 续传（脚本会拦截无意识重发），**不要声称完成，也不要等用户提醒才处理**。

## 最终回复

给出：飞书文档链接、本地交付目录、本地 XMind 文件路径（`$D/mindmap.xmind`）、用例数（P0/P1/P2）、Top 待确认项。导图使用提示：**打开飞书文档复制「用例设计思维导图（PlantUML）」代码块 → 清空飞书画板 PlantUML 编辑框 → 只粘一次**；不要从对话复制（长行会折断）。末尾提示：执行中发现的新缺陷/回归点，可后续单独 ingest 回 qa-knowledge-base。

## 交付前自检（validate 管不到的部分）

- [ ] 风险判断是判断而非复述，真正驱动了 P0 排序。
- [ ] 关键功能点用了对应方法（边界值/判定表/状态迁移…），不是平铺场景。
- [ ] 每个操作可直接执行，用的是 PRD 真实入口、词、字段、阈值。
- [ ] 随手挑几条从根读到叶子：不翻 PRD 也知道在哪个端哪个页面、做什么、看什么。
- [ ] 图/表未保真读取、未解析块、历史不可达都已写进待确认。
- [ ] Top 1-3 高风险历史命中若 notes 不足，已回看 raw/原链接，或已写入待确认。
