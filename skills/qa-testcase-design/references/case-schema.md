# 测试用例中间产物结构

本文件只定义 `testcases.md` 的正文结构、用例叶子、优先级和覆盖自检表。文件落盘与发布规则见 `references/output-files.md`；PlantUML 转换规则见 `references/mindmap-plantuml.md`。

- `testcases.md`：完整结构化测试用例正文，供 QA 执行和评审。
- `history-hits.md`：v2 启用 qa-knowledge-base 时的历史检索证据交付附录，记录检索词组、命中取舍、深读 notes 和编入位置；不写入 qa-knowledge-base，不进思维导图。

所有正文、覆盖自检表、历史检索证据必须使用同一组稳定用例 ID，避免追踪对不上；思维导图默认隐藏内部 ID，只显示用例标题。

交付目录与文件校验见 `references/output-files.md`。交付前必须跑 `scripts/validate_output.py`；校验失败时先修文件结构和 ID 引用，再交付给用户。

## 历史补充（qa-knowledge-base，已启用）

历史补充不新增额外块，也不改变叶子格式。历史命中必须落到风险判断、showcase（提测准入）、用例设计（业务功能用例）、APP 常驻维度补充、风险与待确认或覆盖自检表；不能把 qa-knowledge-base 命中原文直接当用例贴进来。

`history-hits.md` 是交付附录：记录检索词组、命中笔记、保留/丢弃理由、是否深读 `notes/*.md`、最终编入位置。它服务追溯，不改变 `testcases.md` 的 7 块骨架。

覆盖自检表**必须包含 `历史回归` 维度**：有相关历史线索时标已覆盖/待确认，并关联对应用例 ID；未命中相关历史时标 N/A 并说明“qa-knowledge-base 未命中相关历史”；未读时说明“未读 qa-knowledge-base”。历史与 PRD 冲突时，进入第 6 块「风险与待确认」，不覆盖 PRD。

## 输出骨架（顺序固定，7 块）

1. 需求理解（目标 / 入口 / 用户路径 / 状态 / 端 / 接口 / AB / 埋点 / 验收口径）
2. 风险判断（这次最该测什么 + 理由，非中性复述）
3. showcase（提测准入）
4. 用例设计（按业务功能 / 需求类目组织）
5. APP 常驻维度补充
6. 风险与待确认
7. 覆盖自检表

P0/P1/P2 是 `priority=P0/P1/P2`，只体现在用例 ID、覆盖自检表和执行优先级里；**不要把 P0 主流程 / P1 重要场景 / P2 边界兼容当成正文一级目录**。正文一级目录必须服务读者理解本次需求：优先按业务功能、需求类目、用户路径、状态机或核心对象划分。

## 需求理解写法

第 1 块「需求理解」必须用 `- ` 无序列表，至少包含 `目标`、`入口`、`端范围` 三项；可按需求补 `用户路径`、`数据/埋点`、`配置/AB`、`验收口径`、`待确认`。不要写成长段落，飞书发布后会降低可扫读性；`scripts/validate_output.py` 会拦截段落化输出。

## 风险判断写法

第 2 块「风险判断」要能被一眼读完，不要写成一大坨长段落。

- 先一句话点题「本次最该测什么」，再用 **3-5 个 `- ` 无序列表要点**展开理由（每个要点一句话：牵动的模块 / 状态联动 / 历史风险 / 数据一致性等）。
- 每个要点独立成行，避免用分号把 5 件事串成一句。
- 保持判断性表述（"最该测""最容易崩在"），不要退化成中性复述。

## showcase（提测准入）

`showcase（提测准入）` 是从本次需求的核心主路径中提取的演示测试 case，供开始提测时现场演示/冒烟。它不是开发自测附录，也不是完整回归集；它的标准是：**这些 case 不通过，就不达到提测标准**。

- 通常抽 1-5 条，优先覆盖“入口 → 核心操作 → 核心反馈 → 核心数据/回顾”的闭环。
- 复杂交互类需求要覆盖最关键状态迁移，例如：领读 → 抢答/收音 → 识别反馈 → 跳过兜底 → 回顾卡。
- showcase 使用同一套用例叶子格式和稳定 ID，可使用 P0 ID；同一 ID 不要再在「用例设计」里重复写一遍。
- 覆盖自检表必须有 `showcase（提测准入）` 维度，并说明它是否满足提测准入。
- `scripts/validate_output.py` 会强制 showcase 为 1-5 条；超过 5 条说明你把完整回归集误放进提测准入。

## 用例设计（按业务功能 / 需求类目组织）

第 4 块是完整用例主体。分组原则：

- 优先按 PRD 的业务功能、需求类目、用户路径、状态机、核心对象划一级/二级目录，例如“练习提醒 / 提醒设置 / 关闭提醒”或“新版跟读组件 / 语音识别反馈 / 超时跳过”。
- 层级不限制死，允许 3/4/5/6 层；但每层必须有真实区分度，不要为了凑层级机械套模板。
- 同一个功能点下可以有多条用例；每条用例下面的「前置 / 操作步骤 / 预期结果」在 PlantUML 中作为子节点展示。
- P0/P1/P2 不作为分组依据。需要表达优先级时，靠用例 ID 和覆盖自检表。

推荐 Markdown 形态：

````markdown
## 4. 用例设计（按业务功能 / 需求类目组织）

### 新版跟读组件

#### 语音识别反馈

```text
[P0-01] 高分发音后展示绿色反馈并进入下一步｜前置：用户进入 lesson_speech_recognition 开启的新跟读组件，麦克风权限已允许｜步骤：点击开始跟读，清晰读出目标词 "wheat"，等待识别结果返回｜期望：目标词音素反馈显示绿色，Max 播放成功反馈动画，课程进入下一步，识别结果与回顾页一致
[P1-01] 识别服务超时后展示可恢复兜底｜前置：用户处于跟读收音中，可通过代理模拟识别接口超时｜步骤：读出目标词后等待识别接口超时，点击重试，再次完成跟读｜期望：首次超时展示明确重试/跳过入口，不产生成功结果；重试成功后状态恢复并继续课程
```
````

## APP 常驻维度补充

第 5 块只放那些没有自然落入第 4 块、但 APP 测试长期必须过闸的补充点。常驻一级维度：

- 边界/兼容
- 跨端联动
- 后端/配置
- AB
- 埋点
- 多语言兼容

写法规则：

- 如果某个常驻维度已在第 4 块业务用例里充分覆盖，第 5 块可以写 `无补充，已在 P0-xx/P1-xx 覆盖`，避免重复。
- 如果本需求完全不涉及某维度，写 `无`，并在覆盖自检表标 N/A。
- 常驻维度不是垃圾桶；只能补充真实风险，不要为了每个维度凑一条空泛用例。

**第 4 块 vs 第 5 块「后端」怎么分（避免摆放不一致）**：

- 与**本需求业务强绑定**的后端用例进**第 4 块**（放在对应业务功能下），例如「跟读完课上报后端记分」「learning asset 词库落库」。
- **通用后端面**（不特定于本需求、任何写接口都要过的）进**第 5 块「后端/配置」**，例如幂等/重复提交、字段兼容/缺失、配置灰度回退这类模板化风险。
- 拿不准时放第 4 块（跟着业务走，读者更好找）；同一条用例只放一处，别两块都写。

## 用例叶子格式

```text
[P0-01/P1-01/P2-01] 用例标题｜前置：...｜步骤：...｜期望：...
```

- 步骤具体可执行；禁止「验证功能正常」「检查页面无问题」这类空泛叶子。
- 不编造产品逻辑、接口字段、AB 策略、视觉标准。
- 依赖未确认信息的用例，标题后加「（待确认）」；详细原因统一写入第 6 块「风险与待确认」。
- 不在叶子里塞 `来源/待确认` 字段，避免叶子过长、观感变差；粗粒度追溯靠业务功能分组、稳定 ID、覆盖自检表和 `history-hits.md`。
- ID 规则：每个优先级内从 `01` 递增，例如 `[P0-01]`、`[P0-02]`、`[P1-01]`；ID 的优先级含义等价于 `priority=P0/P1/P2`。正文、覆盖自检表、`history-hits.md` 必须引用同一个 ID；`mindmap.puml` 默认隐藏内部 ID，只显示用例标题。
- 标题要描述可判定行为，不写“测试 XX 功能”；前置、步骤、期望尽量使用 PRD 中的真实入口、状态、词、配置名、字段名或示例数据。
- **标题禁带来源/归属标注**（如「历史回归」「Unity 风险」「后端风险」「端差异」这类括号标注）：它们会被 `md_to_mindmap.py` 带进思维导图节点、触发 `validate_output.py` 附录污染拦截。历史/风险库来源只写进覆盖自检表「说明」与 `history-hits.md`；端差异等测试提示写进步骤/预期或自检表说明。标题里唯一允许保留的括号是「（待确认）」。

## 复杂交互拆解规则

从旧跟读组件类需求吸收的规则：复杂交互不要按优先级平铺，先把 PRD 表格和流程图拆成状态机/分支矩阵，再落成用例。

- 状态表（如 Max 默认静止 / 领读中 / 聆听中 / 读对反馈 / 出场离场）→ 状态迁移用例。
- 新旧差异表（如收音反馈 / 倒计时 / 角色 / 评分外露）→ 回归对比用例。
- 分支流程（如提前发声 / 未提前发声 / 发音正确 / 发音错误 / 未发声超时 / 失败 2 次跳过）→ 判定表或场景法用例。
- 行为绑定数据（如点击跳过 → `speech_skip=true`）→ 行为 + 埋点成对校验，不把埋点孤立成空泛节点。
- 视觉/音频/动画联动（如光波颜色、随音量波动、错误音效、Max 动画）→ 同一用例里写清楚联动预期。

## 思维导图映射边界

`testcases.md` 的 P0/P1/P2 是优先级属性，**不是**思维导图一级菜单。这里仅定义正文侧必须提供给转换脚本的结构信号：

- 第 4 块标题层级提供业务/功能路径。
- 第 5 块标题层级提供 APP 常驻维度补充路径。
- 覆盖自检表提供用例归属和重复覆盖追踪。
- 风险判断、风险与待确认、覆盖自检表、`history-hits.md` 不作为思维导图节点来源。

具体 PlantUML 节点、full/compact 模式、粘贴注意事项和富层级样例，统一看 `references/mindmap-plantuml.md` 与 `references/example-mindmap-rich.puml`。

## 优先级定义

| 优先级 | 含义 |
|---|---|
| P0 | 不通过不能发版：主链路、启动、登录、奖励、学习进度、热更、核心接口、核心配置 |
| P1 | 重要路径：常用分支、配置/AB、跨端状态、异常恢复、弱网恢复 |
| P2 | 边界、兼容、探索、低频状态、文案/视觉细节 |

## 覆盖自检表（每次必出）

| 维度 | 状态 | 对应用例 | 说明 |
|---|---|---|---|
| showcase（提测准入） | 已覆盖 | P0-01, P0-02 | 覆盖入口到结果；方法=场景法 |
| 新版跟读组件 | 已覆盖 | P0-03, P1-01 | 覆盖语音识别反馈和状态恢复；方法=状态迁移 |
| Unity | N/A | - | 本需求不涉及 Unity 课程资源 |
| AB 配置 | 待确认 | P1-03 | PRD 未说明分组和灰度策略；方法=判定表 |

### 覆盖自检硬规则

- 每条用例 ID 都必须至少出现在覆盖自检表一次；漏写会被 `validate_output.py` 拦截。
- 覆盖自检表必须包含 `showcase（提测准入）`、`历史回归` 和 APP 常驻维度：`边界/兼容`、`跨端联动`、`后端/配置`、`AB`、`埋点`、`多语言兼容`。
- APP 常驻维度与本需求无关时写 `N/A` 并说明理由；不要删除维度。
- 状态只能写 `已覆盖`、`N/A`、`待确认`。
- `已覆盖` 必须关联至少一个用例 ID；`N/A` 不应关联用例 ID；`待确认` 要关联受影响用例或 Q 项。
- 标题带「（待确认）」的用例，必须在第 6 块「风险与待确认」中用 Q 项说明，并在影响列写到对应 ID。

### 状态判定规则

| 状态 | 判定标准 |
|---|---|
| 已覆盖 | 该维度与本需求相关，且 >=1 条可执行用例覆盖 |
| N/A | 与本需求明显无关，并写明理由 |
| 待确认 | PRD 没写清、无法判断是否需测；写原因 + 影响哪些用例 |

方法标注只服务自检和复盘，不进入每条叶子的长描述。禁止只写「已检查」「正常验证」。自检表要能让 QA 一眼看出漏没漏。
