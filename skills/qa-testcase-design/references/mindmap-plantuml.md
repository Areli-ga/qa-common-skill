# 飞书思维导图输出（PlantUML mindmap）

用例中间产物 → PlantUML `@startmindmap` 文本 → **写成 `.puml` 文件** → 用户打开文件、全选复制，粘进飞书画板 PlantUML 输入框 → 渲染成接近原生样式的思维导图。零依赖、零 API。

> **生成方式：跑脚本，别手抄。** 用 `python3 scripts/md_to_mindmap.py testcases.md mindmap.puml` 确定性转换；默认输出完整评审图，用户只要主结构时加 `--compact`。AI 手动逐行渲染容易重复/断行/报错——本文件是脚本背后的规则说明，不是让你手抄的模板。

标准正文样例见 `references/example-testcases.md`；富思维导图样例见 `references/example-mindmap-rich.puml`。本文件只说明 PlantUML 转换规则、飞书粘贴注意事项和最小语法约束。

## 两条生成路径（别混）

1. **默认（build）**：脚本读 `testcases.md` 的用例 + 覆盖自检表，自动按业务功能归类，层级到 `业务功能 → 子模块 → 用例 → 前置/操作步骤/预期结果`（约 5 层）。日常走这条，确定性、防断行。
2. **进阶（extract）**：当某需求确实要更深结构（如等价类/边界值挂「测试数据 A/B/C」那层，见 `example-mindmap-rich.puml`），可在 `testcases.md` 里**直接写一段 ` ```plantuml ` 的 `@startmindmap` 块**；脚本检测到就**原样提取**、不再自动 build。这条能表达任意深度，但层级合法性要自己保证。

> `example-mindmap-rich.puml` 里的「测试数据组」7 层富样例属于第 2 条（AI 直接写块），**不是** build 从普通叶子自动长出来的；标准正文样例仍以 `example-testcases.md` 为准。

## ⚠️ 铁律：必须落成文件，别让用户从对话里复制

长行（如「期望：…」）在聊天框会**软换行**；用户从对话复制时，折行处会混入真实换行，把一个节点断成两行、第二行没有 `*` 前缀 → **飞书解析报错**。这是唯一反复踩的坑。
所以生成 PlantUML 后**必须用脚本落成 `.puml` 文件**（scratchpad、临时目录或用户指定目录），并提示用户「**先清空飞书 PlantUML 编辑框 → 打开 `.puml` → 全选 → 复制 → 粘进飞书 → 只粘一次**」。绝不把整段长文本直接丢进对话让用户复制。

生成后按 `references/output-files.md` 跑 `scripts/validate_output.py testcases.md --history history-hits.md --mindmap mindmap.puml`；校验失败先回修文件，不让用户手动修 PlantUML。

## 生成规则

- `*` 个数 = 层级：根 `*`、一级分类 `**`、子模块/功能点 `***`、用例 `****`、前置/操作步骤/预期结果 `*****`。复杂需求可以继续自然加深层级，不限制死 3 层或 5 层。
- 首尾必须 `@startmindmap` / `@endmindmap`；一行一节点：`<N个*><空格><文字>`。
- 层级每次最多 +1（不能从 `**` 直接跳 `****`）；同级可任意多个。
- 思维导图隐藏内部用例 ID（如 `[P0-01]`），ID 只保留在 `testcases.md`、覆盖自检表和 `history-hits.md` 中追踪。
- **需求理解 / 风险判断 / 风险与待确认 / 覆盖自检表 / history-hits.md 不进入思维导图**：这些内容已经在 Markdown 正文或附录展示。
- **P0/P1/P2 不作为思维导图一级菜单**：它们只是优先级属性和 ID 追踪，图里的一级菜单按业务功能/覆盖维度生成。
- 中文、`(待确认)`、`→`、`/`、`_`、`，`、`'` 均**原样**，无需转义（已实测飞书全支持）。
- 用 PlantUML（`@startmindmap`），**不要用 Mermaid**——Mermaid 把 `[P0]`、`(待确认)` 的方括号/圆括号当节点形状语法，用例全是括号会全崩。

## 输出模式

- **默认模式：full**。输出 `showcase（提测准入）`、业务/功能一级分类、APP 常驻维度、用例标题，以及每条用例的 `前置：...` / `操作步骤：...` / `预期结果：...`。
- **compact 模式（用户只要主结构时用 `--compact`）**。保留一级分类和用例标题，不挂前置/操作步骤/预期结果。

## 文本清洗

- 每个节点必须是**单行节点**：去掉换行，把 `\r` / `\n` / Markdown `<br>` 统一替成空格。
- 合并连续空格，首尾去空白，避免飞书画板 PlantUML 把空白解析成异常节点。
- 替换 @startmindmap 和替换 @endmindmap：如果业务文本里出现这两个词，改成 `startmindmap` / `endmindmap`，避免提前结束图。
- 节点文字过长时优先压缩标题；full 模式把执行细节放到子节点，避免同一节点过长。

## testcases.md → mindmap 映射

- **根（`*`）**：`<需求名>｜测试用例`
- **一级（`**`）**：`showcase（提测准入）` + 本次需求业务/功能维度 + APP 常驻维度（`边界/兼容`、`跨端联动`、`后端/配置`、`AB`、`埋点`、`多语言兼容`）。
- **showcase（提测准入）**：从核心主路径提取的演示测试 case，用于开始提测时现场演示；这些 case 不通过，不达到提测标准。
- **业务/功能维度**：优先来自覆盖自检表，例如“新版跟读组件接入 / 音素红黑绿打分 / Unity 单词回顾”。不要强行改成 P0/P1/P2。
- **APP 常驻维度**：有用例就正常挂二/三级节点；无用例时保留一级节点并写 `无`。
- **重复覆盖**：同一条用例只在图里出现一次；它兼顾的其他覆盖维度通过覆盖自检表追踪，不在图里复制节点。
- **未映射用例**：覆盖自检表漏写的 case 先按标题关键词归入具体业务/常驻类目；仍无法判断时才进入 `其他业务场景`。**图里出现 `其他业务场景` 就是信号——说明这些用例没进覆盖自检表，回去把它们补进自检表对应业务维度，图会自动干净。**
- **用例标题**：隐藏内部 ID，可保留业务标题里的 `(待确认)`。
- **用例详情**：默认在用例下挂 `前置：...` / `操作步骤：...` / `预期结果：...` 三个子节点。
- **正文与附录**：需求理解、风险判断、风险与待确认、覆盖自检表、history-hits.md 不进思维导图。

## 最小语法片段

    @startmindmap
    * 需求名｜测试用例
    ** 一级分类
    *** 子模块
    **** 用例标题
    ***** 前置：...
    ***** 操作步骤：...
    ***** 预期结果：...
    @endmindmap

这段只用于说明 `*` 层级语法，不代表完整业务输出结构；完整复杂样例、showcase、测试数据组和多层级拆法看 `references/example-mindmap-rich.puml`。
