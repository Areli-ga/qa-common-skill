## A. 覆盖维度（逐维过闸）

每个维度只能标 `已覆盖 / N/A / 待确认`，禁止默默跳过。

### 产品链路

- 启动：冷启动、杀进程重启、首装、升级、热更检查、资源下载、失败重试。
- 账号：游客、登录、注册、新老用户、儿童档案、国家码、权限弹窗（产品无会员分层，会员维度直接 N/A，见 `code-risk-backend.md`）。
- 学习：地图、推荐课、进课、课中互动、完课、退出、重进、结算、奖励、进度同步。
- 内容：课程资源、故事书、挑战课、报告、证书、明日预告、搜索、多语言文案。
- 运营：ABTest、后台开关、弹窗、Banner、活动、奖励中心、扭蛋、配置灰度。

### 技术端覆盖

| 端/模块 | 必测关注 |
|---|---|
| Android 原生 | 权限、返回键、生命周期、低端机、安装升级、系统版本、网络切换 |
| iOS 原生 | 权限、前后台切换、弱网恢复、内购/登录态、不同机型安全区 |
| Unity | 资源加载、场景切换、动画/Spine、性能、内存、崩溃、课中状态恢复 |
| H5 | WebView 判定、Bridge 时序、登录态/语言、路由、缓存/离线包、资源 CDN、语音/音频、埋点、旧 WebView 兼容 |
| Flutter | 页面状态、路由栈、原生桥、渲染、键盘/安全区、异步加载 |
| 后端 | 接口入参/出参、错误码、幂等、超时、重试、数据一致性、灰度配置 |

### 通用场景

- 主流程：按 PRD 用户路径从入口到结果完整走通。
- 反向/中断：中途退出、断网、杀进程、切后台、重复点击、快速切换。
- 状态矩阵：新/老用户、未/已解锁、未/已完成、有/无奖励、有/无配置。
- 弱网：无网、2G/3G、超时、资源下载中断、接口失败后恢复。
- 兼容：不同系统、屏幕、低端设备、横竖屏/安全区。
- 数据一致性：客户端展示、后端记录、进度、奖励数量、埋点与配置命中一致。
- 回归：受影响模块老路径、相邻入口、历史缺陷路径、提测说明关联模块。

### 风险提示

- 多端联动易漏端间状态同步；Unity 资源/动画变更易白屏、卡死、闪烁、内存上涨。
- 后台配置/AB 未写清必须标待确认，并要求测试前固定配置。
- 热更/资源/启动链路失败必须验证可恢复和用户可理解的失败状态。
- PRD 只有视觉稿时，补问交互、接口、边界、空态、异常和灰度策略。

## B. 测试设计方法（出例前给每个功能点挂 1-2 个方法）

§A 定「面」，本节定「面 × 方法」。不是每个方法都用，按特征选 1-2 个。

### 从 PRD 到用例 6 步

1. 拆对象：用户、入口、页面/组件、核心对象、端、接口、配置、埋点。
2. 拆规则：把正文、**表格**、流程图里的条件、状态、阈值、枚举、异常分支抽出来，逐条编号写进需求理解的「业务规则追溯」表（见 §C）。
3. 建模型：多状态→状态迁移表；多条件→判定表；多环境→因子水平表；端到端→基本流/备选流。
4. 选方法：按下方决策表挂方法，不凭感觉列场景。
5. 选数据：用 PRD 真实入口、词、参数、配置名、字段名、阈值；没有就写待确认，不用「某数据」糊弄。
6. 写叶子：能执行、能判定、能追溯到需求规则或历史风险；写完进覆盖自检表。

### 需求拆解检查单

| 拆解项 | 要问的问题 | 容易漏的用例 |
|---|---|---|
| 用户/身份 | 谁能看到/操作？登录态、儿童档案是否影响？ | 未登录、切换孩子、权限不足 |
| 入口 | 从哪些入口进？冷/热启动、返回再进是否一致？ | 深链、Push、活动入口、旧入口复用 |
| 状态 | 有哪些状态？靠什么事件切换？ | 中断恢复、非法事件、重复触发、状态回滚 |
| 数据 | 从哪来、写到哪、哪里展示？ | 前端展示与后端落库不一致、缓存脏数据、重复提交 |
| 配置/AB | 开关、灰度、国家、语言、版本怎么命中？ | 命中/未命中、配置缺失、旧版本兼容 |
| 端范围 | Android/iOS/Unity/H5/backend 哪些参与？ | 单端通过但跨端回调、容器生命周期、端差异 |
| 失败恢复 | 接口/识别/资源失败、弱网如何恢复？ | 只测报错不测重试/跳过/恢复后数据状态 |
| 埋点 | 哪个行为触发哪个事件，字段从哪取？ | 事件重复、失败分支不上报、字段空/null/旧值 |
| 历史回归 | qa-knowledge-base 命中过哪些旧规则、旧边界、相邻入口？ | 旧入口、旧配置、旧埋点、旧资源被本次改动影响 |

### 充分性标准

- 每条业务规则 ≥1 正向路径；有明确反向/异常规则必须覆盖反向。
- 每个状态覆盖进入、退出、关键中断；状态机覆盖合法迁移 + 关键非法迁移。
- 每个数值/次数/长度/时间阈值覆盖 边界内、正好边界、越界 1 点——**三个点各自一条用例**。
- 每个配置/AB 覆盖 命中、未命中、缺失/关闭；口径未写进「风险与待确认」。
- 每条核心数据链路覆盖 展示、写入、刷新/回访、跨端或下游消费一致性。
- 每个失败分支验证 提示 + 重试/跳过/返回 + 恢复后继续。
- **PRD 表格里的每个数值**要么落进某条用例，要么在「风险与待确认」说明（validate 数值对账会列出遗漏；链接、文档信息行（需求背景 / 产品目标等）、「1 + 1」式加法拆分不参与对账）。

### 方法速查（触发 → 操作 → 陷阱）

1. **等价类**：输入/参数/枚举/身份态 → 有效类 + 无效类各 ≥1 → 漏无效类、类划得太粗。
2. **边界值**：数值/数量/长度/次数/时间 → min−1/min/min+1、max−1/max/max+1，含 0、空、超长 → 只测中间值。
3. **判定表**：多条件组合决定结果（开关/权限/AB×国家×身份）→ 条件桩×动作桩，每条规则 1 例；输入间有依赖时先画因果图再转判定表 → 漏组合、未化简。
4. **状态迁移**：状态机/生命周期/计数器/播放下载态 → 每状态、每合法迁移、关键非法迁移（该状态不该响应的事件）→ 漏非法事件与中断恢复。
5. **场景法**：端到端多步骤流程 → 基本流 + 备选流 + 异常流，异常要闭环到恢复 → 只走 happy path。
6. **正交/Pairwise**：机型×系统×网络×语言×分辨率 → 两两覆盖 + 必测强组合 → 盲目全组合或只测默认。
7. **错误推测**：收尾兜底、历史坑 → 空值/超长、重复提交、连点、并发、杀进程、断网重连、权限拒绝、时区/多语言、缓存脏数据 → 当唯一方法用。

### 特征 → 方法决策表

| 特征 | 优先用 |
|---|---|
| 输入框 / 参数 / 枚举 / 状态 | 等价类 + 边界值 |
| 数值 / 数量 / 长度 / 次数 / 时间范围 | 边界值 |
| 多条件组合决定结果（开关/权限/AB） | 判定表 |
| 状态机 / 生命周期 / 计数器 | 状态迁移 |
| 端到端用户流程 | 场景法 |
| 多端 / 多环境兼容 | 正交 / Pairwise |
| 收尾兜底、历史易错点 | 错误推测 |

方法只用于设计推导；输出时不展开方法论，只在覆盖自检表「说明」短标 `方法=xxx`。

### 低质量用例反例

| 反例 | 问题 | 应改成 |
|---|---|---|
| 验证跟读功能正常 | 无入口、数据、操作、判定 | 进入 lesson_speech_recognition 课程读出 "wheat"，期望：目标词展示绿色反馈 |
| 检查埋点正常 | 埋点脱离行为 | 点击跳过后，期望：`speech_skip=true` 只上报一次 |
| 测试弱网 | 无网络条件和恢复判定 | 3G 下提交识别结果、接口 8s 超时，期望：展示重试入口 |
| Android/iOS 兼容 | 太泛 | Android 14 首次进入跟读拒绝麦克风权限，期望：展示权限引导 |
| 期望：A 正确；B 同步；C 不残留 | 一行打包 3 个断言 | 拆成 3 条原子用例，挂在同一分解树节点下 |

## C. 输出结构（testcases.md）

### 6 块骨架（顺序固定，标题逐字一致）

文件首行写 `# <需求名>`（作为导图根节点与飞书标题兜底），随后：

1. `## 1. 需求理解`
2. `## 2. 风险判断`
3. `## 3. 用例设计（按端 / 页面 / 功能组织）`
4. `## 4. APP 常驻维度补充`
5. `## 5. 风险与待确认`
6. `## 6. 覆盖自检表`

P0/P1/P2 只是 `priority` 属性，体现在用例 ID、自检表和执行优先级；**禁止作为正文一级目录**。

### ⚠️ 机器校验硬规则（违反则 `validate_output.py` FAIL、无法发布）

1. 用例行必须写在 ` ```text ` 代码块内；裸列表 `- [P0-01] …` 不被识别。
2. 行首直接是 ID，不带 `- `；ID 形如 `P0-01`（两位或三位数字），每个优先级内从 01 递增。
3. 六块标题与上方骨架逐字一致（`## 3. ` 序号可有可无），第 3 块必须写全称。
4. 每条用例写成 `操作或条件｜期望：结果` 两段；出现 `｜前置：` 或 `｜步骤：` → FAIL（前置改为分解树标题，步骤并入操作）。
5. 粒度闸：第 3 块单个 `###` 组下用例 >4 条且无 `####` 细分 → FAIL。
6. 原子闸：`期望` >80 字 FAIL（>50 字 WARN），操作 >40 字 WARN；`期望` 内用「；」或「，且 / ，并且 / ，而且 / ，同时 / ，并」串联 ≥3 个结果 FAIL（2 个 WARN）。
7. 每条用例 ID 至少进覆盖自检表一次；带「（待确认）」的用例必须在第 5 块被 Q 项引用。
8. 追溯闸：第 1 块必须有 `### 业务规则追溯` 表；每条规则编号唯一、规则与来源非空；落点至少一个已存在的用例 ID 或第 5 块已定义的 Q 编号，引用不存在的 ID / Q 也 FAIL。
9. 阻断闸：第 5 块表头为 `编号 | 级别 | 问题 | 影响`，级别只能是 `阻断 / 已确认 / 记录`；存在 `阻断` 行即 FAIL（先停下问用户）；`已确认` 行的问题列必须含「用户确认：」。
10. 按端分组闸：需求理解「端范围」同时写了 Admin（或后台）和 App（或 Android / iOS / Unity / 客户端）时，第 3 块每个 `###` 必须以端名开头（`Admin` / `App` / `服务端` / `H5` / `Web`），且至少 2 个 → 否则 FAIL。
11. 命名闸：第 3、4 块的分组标题出现表号/图号（`表 4`、`图02`）、规则编号（`R05`）或「示例」→ FAIL。

最小骨架：

```text
[P0-01] 点击 Max 卡片｜期望：Max 成为被帮对象
[P1-01] 点击 Max 卡片｜期望：Max 在左台，Lily 在右台
```

### 1. 需求理解

`- ` 无序列表，至少含 `目标`、`入口`、`端范围`；按需补 `用户路径`、`状态`、`接口`、`数据/埋点`、`配置/AB`、`验收口径`、`待确认`。不写长段落（validate 拦截）。

列表之后是 `### 业务规则追溯` 表（本块最后一部分，防漏的追溯底座）：

| 编号 | 规则 | 来源 | 落点 |
|---|---|---|---|
| R01 | 连续读错 2 次后解锁跳过按钮 | 表2 第3行 | P0-08、P0-09 |
| R02 | 音素分低档展示红色 | 正文「打分规则」 | P0-05、Q1 |

- 一条规则 = PRD 里一个可验证的业务约定：条件→结果、状态迁移、阈值、配置口径、埋点触发。分支表按行拆；同一行多个数值可合并为一条（数值由数值对账兜底）。
- 来源必填：正文段落名 / 表N（第几行）/ 图NN，方便评审对照 PRD 找漏拆的规则。图里有、正文没有的规则也要入表。
- 落点写覆盖该规则的用例 ID；PRD 没写清、暂时无法出例的写第 5 块 Q 编号。落点为空 = 这条规则漏测。
- 只收 PRD 规则；常驻维度、风险库、历史回归补出来的用例不必反向挂到这里。

### 2. 风险判断

一句话点题「本次最该测什么」+ **3-5 个 `- ` 要点**（每点一句：牵动模块/状态联动/历史风险/数据一致性）。保持判断性表述（"最该测""最容易崩在"），不中性复述，不用分号把 5 件事串一句。它决定 P0 排序，不一碗水端平。

### 3. 用例设计 —— 先树后例

写用例行之前，先用多级标题（`###`、`####`、`#####`、`######`、`#######`……）把需求拆成**分解树**，用例只挂叶层。导图由这棵树确定性生成——**树有多深图就有多深，结构塞进用例行文字里=结构直接丢失**。

- **第一层按端分**（`###`）：测试者在哪操作就挂在哪。PRD 同时涉及 Admin 和 App 时，先分 `### Admin`、`### App`；服务端有需要直接调接口验证的内容才加 `### 服务端`；独立于 App 的网页加 `### H5` / `### Web`。App 内的原生、Unity、H5 页面都归 `### App`。只涉及一个端时，第一层直接按页面/模块分。
- **往下按测试链路逐层细化，层数不设上限**：端 → 页面/模块（如 Admin 单元设置、单元内容；App 学习路径、复习单元详情）→ 功能区/控件 → 条件/状态/数据 → 用例的操作 → 结果。链路有几层就写几层，`#######` 以下照样可用；每层要有真实区分度，禁止「功能点」「其他」占位名；P0/P1/P2 不作分组依据。
- **跨端用例挂在看结果的那一端**，另一端的操作写成前置节点：例如 `### App` → `#### 复习单元详情` → `##### 前置：Admin 禁用第 14 单元` → 用例 `打开第 15 单元复习详情｜期望：近期卡组改为第 13、11 单元的词`。同一规则在两端都能看到时，挂在最直接可见的一端（如 Admin 只读展示的计算结果挂 Admin），另一端只测本端特有的表现，不重复验同一个计算。
- **节点用测试者视角命名**：只用页面名、按钮/字段名、真实数据和状态描述，让人照着就能找到地方。禁止用 PRD 章节名、表号/图号、规则编号、产品概念词做分组（反例：「表 4 示例路径」「排除规则」「开局现算」「只看位置不看进度」）；规则覆盖靠业务规则追溯表保证，不靠分组名。
- **可读标准**：从根读到任一叶子，连起来就是一句完整的测试步骤——在哪个端哪个页面、什么条件、做什么、看到什么；不翻 PRD 也知道怎么测。
- **分解粒度硬要求**：
  - PRD 数值设定**逐项成节点**：血量、每档伤害、触发次数、上限阈值……各自一个节点或独立用例，禁止合并进一条期望；
  - 分支表/反馈表**逐行成节点**：正确 / 错 1 / 错 2 / 保底 / 超时 各自一个子节点；
  - 每个结局/状态**各自成节点**：触发条件、演出明细、结算结果分开验证。
- **原子用例**：一条只验证**一个可判定断言**。两个数值、两条链路、两种状态 → 拆两条。反例：「初始血量分别为 2 与 7；每读对 −1；两者同步下降」是三条用例。
- 同一叶层的多条原子用例放同一个 ` ```text ` 块。
- **前置作为树节点**：某组用例共用的前置条件（配置值、历史状态、端）写成一层标题，如 `##### 前置：配置目标词数 N=5`、`##### 已失败 1 次`，导图里自然成为上层节点；通用环境（已登录、新版本）不写。
- **同操作多结果**：一个操作有几个可判定结果就写几条用例，操作文字保持一致，导图会把它们合并到同一个操作节点下、结果并列成叶子。

**复杂交互拆解**（先拆模型再落用例）：

| PRD 里的结构 | 落成 |
|---|---|
| 状态表（静止 / 领读中 / 聆听中 / 读对反馈 / 离场） | 状态迁移用例 |
| 新旧差异表（收音反馈 / 倒计时 / 角色 / 评分外露） | 回归对比用例 |
| 分支流程（提前发声 / 正确 / 错误 / 超时 / 失败 2 次跳过） | 判定表或场景法用例 |
| 行为绑定数据（点击跳过 → `speech_skip=true`） | 行为 + 埋点成对校验，不孤立写「埋点正常」 |
| 视觉/音频/动画联动（光波颜色、错误音效、Max 动画） | 每种联动各一条原子用例，挂同一交互节点下 |

### 4. APP 常驻维度补充

常驻一级维度（`###` 标题逐字使用）：**边界/兼容、跨端联动、后端/配置、AB、埋点、多语言兼容**。

- 已在第 3 块充分覆盖的维度写 `无补充，已在 P0-xx 覆盖`；完全不涉及写 `无` 且自检表标 N/A；不为凑维度写空泛用例。
- 后端摆放：与本需求业务强绑定的后端用例进第 3 块对应功能下；通用后端面（幂等/重复提交、字段兼容/缺失、灰度回退）进第 4 块「后端/配置」；拿不准放第 3 块；同一条只放一处。

### 用例叶子格式

```text
[P0-01] 操作或条件｜期望：结果
```

- 写法对齐团队思维导图：一条用例 = 树上一条路径，操作是中间节点，结果是叶子；两段都写短句，不写完整句子。
- 操作写真实动作或触发条件，带真实数据（入口、词、配置值、次数）；期望写一个可判定结果（页面反馈、状态、数据、埋点之一）。
- 前置不写进叶子，按上节「前置作为树节点」处理。
- 操作写具体动作，不写「测试 XX 功能」；禁「验证功能正常」「检查页面无问题」「正常显示」「按预期展示」。
- 不编造产品逻辑/接口字段/AB 策略/视觉标准。
- **标题禁带来源/归属括号标注**（「历史回归」「Unity 风险」「后端风险」「端差异」等会污染导图）；唯一允许的括号是「（待确认）」。来源只写进自检表「说明」与 `history-hits.md`。
- 依赖未确认信息的用例标题加「（待确认）」，原因统一进第 5 块 Q 项；叶子里不加 `来源/待确认` 字段。
- ID 在正文、自检表、`history-hits.md` 中保持一致；导图隐藏 ID。

### 优先级定义

| 优先级 | 含义 |
|---|---|
| P0 | 不通过不能发版：主链路、启动、登录、奖励、学习进度、热更、核心接口/配置 |
| P1 | 重要路径：常用分支、配置/AB、跨端状态、异常恢复、弱网恢复 |
| P2 | 边界、兼容、探索、低频状态、文案/视觉细节 |

P0 不宜超过全部用例的一半；全是 P0 等于没有排序（validate 告警）。

### 5. 风险与待确认

表格：`编号 | 级别 | 问题 | 影响`；`影响` 列写受影响用例 ID。历史资料与 PRD 冲突进这里，不静默取舍。

- 来自历史的风险（与 PRD 冲突、口径差异、可能被本次改动影响的旧逻辑）问题列以「历史：」开头。飞书文档不发布 `history-hits.md`，读者只从这张表看到历史风险，所以有风险的历史线索必须落成 Q 项，不能只写在 history-hits 里。

| 级别 | 何时用 | 怎么处理 |
|---|---|---|
| `阻断` | 影响 P0 主链路能否发版；影响接口 / 配置 / AB 发版口径或测试环境前置；历史资料与本次 PRD 目标相反 | 立刻停下问用户；validate 见到阻断行直接 FAIL |
| `已确认` | 用户已答复的阻断项 | 问题列末尾写「用户确认：<答复原话或要点>」，按答复出例 |
| `记录` | 其余待确认：低频边界、端范围未写、旧配置是否复用等 | 不追问，直接写入 |

- 级别由问题的影响决定，不能为了过校验把阻断降成记录，也不能没问用户就写成已确认。

| 编号 | 级别 | 问题 | 影响 |
|---|---|---|---|
| Q1 | 记录 | PRD 未给音素分阈值的取整规则 | P1-03 |
| Q2 | 已确认 | 每局词数上限正文写 12、图 02 写 30。用户确认：以 30 为准 | P1-20 |

### 6. 覆盖自检表

格式：`维度 | 状态 | 对应用例 | 说明`。

| 状态 | 判定标准 | 对应用例列 |
|---|---|---|
| 已覆盖 | 与本需求相关，且 ≥1 条可执行用例覆盖 | 必须 ≥1 个 ID |
| N/A | 与本需求明显无关，说明写理由 | 不得写 ID |
| 待确认 | PRD 没写清、无法判断是否需测 | 受影响 ID，或说明里写 Q 项 |

- 每条用例 ID 至少出现一次。
- 必含维度：`历史回归` + 六个 APP 常驻维度（名称逐字一致）；无关写 N/A，不删除。业务维度按第 3 块端下的页面/模块写，带端名，如 `Admin 单元设置`、`App 复习单元详情`。
- `历史回归`：有线索标已覆盖/待确认并关联 ID；未命中标 N/A 注明「qa-knowledge-base 未命中」；未读注明「未读 qa-knowledge-base」。
- 说明列可短标 `方法=xxx` 与历史来源；禁止只写「已检查」「正常验证」。

示例：

| 维度 | 状态 | 对应用例 | 说明 |
|---|---|---|---|
| 新版跟读组件 | 已覆盖 | P0-03、P1-01 | 方法=状态迁移 |
| AB | 待确认 | P1-03 | 灰度策略见 Q2；方法=判定表 |
| 多语言兼容 | N/A | - | 本需求无新增文案 |

### 历史补充（qa-knowledge-base）

历史命中不是用例，必须重新编译落到：风险判断 / 第 3 块 / 第 4 块 / 风险与待确认 / 自检表说明。不新增块、不改叶子格式、不贴知识库原文；不覆盖 PRD。检索证据记录在 `history-hits.md`（规则见 `history-kb-contract.md`）。

### 思维导图映射

由 `md_to_mindmap.py` 确定性转换，不手写 PlantUML：根=首行 `# 需求名`；一级=第 3 块 `###`（Admin / App 等端）+ 第 4 块六个常驻维度；更深层级=分解树标题，不限层数；用例写成「操作 → 结果」两层：操作节点（隐藏 ID、不带优先级）下挂结果叶子，同一位置操作文字相同的用例合并为一个操作节点。需求理解、风险判断、风险与待确认、覆盖自检表、history-hits 不进导图。细节见 `mindmap-plantuml.md`。
