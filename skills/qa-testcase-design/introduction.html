这是什么 · 大白话

它替你干掉了写用例里最耗时、最容易漏的那部分

写一篇测试用例，真正动脑的"设计"只占一小部分，大量时间耗在读文档、看图、翻往期需求、排版发布上。这条流水线把这些机械活自动化，让人只专注在"验收把关"。

😮‍💨 以前：纯手工，一篇 30 分钟+

  • 逐页读 PRD、一张张看设计图
  • 凭记忆想"这块以前有没有踩过坑"
  • 担心漏测维度，反复对照检查表
  • 手写用例、手动排版、手动发飞书

✅ 现在：一条链接，常规约 15–20 分钟

  • 文档 / 表格 / 图片自动原样抓取
  • 自动翻历史知识库，接上回归点
  • 几十个维度机器逐个过闸，漏了就报错
  • 用例、思维导图、飞书文档一键产出
核心流程 · 从链接到飞书文档

一条链接进来，这样一步步变成测试用例

下面每一步都标了"大白话在干嘛"和"背后调用了哪个文件"。📘蓝=读飞书 · 🟣紫=写飞书 · 🟢绿=质量校验。

1
📂 开工准备
接到需求，建一个专属交付目录，避免多次生成互相覆盖。
总控 SKILL.md · 目录规范 references/output-files.md
2
📥 保真读取 读飞书
把飞书文档里的每一段文字、每张表格、每一张图都原样抓下来存到本地，一个字都不漏；连文档内嵌的电子表格（Sheet）（埋点表、字段表常放这里，平铺看根本看不见）也自动读进来。中断了不用重来：加 --resume 续跑只补缺（图片原子落盘防半截文件，网络抖动自动重试 3 次）。
脚本 read_doc.py（凭证/网络/重试由 lark_common.py 提供）→ 产出 source/ 原料
⚡ 步 2.5 · 三件事同时开工，不排队等（这是提速的关键）
🖼️ 看图代理

专人盯着所有设计图，把图里的文案、字段、数值、状态、流程一张张转录成文字。图多就拆几个人分头看。

→ images-notes.md
📚 翻历史代理

去历史知识库检索"这个模块以前做过啥、埋过啥坑、有哪些回归点"，深读往期笔记。

→ history-hits.md
✍️ 主线自己

同时读正文和表格，用自己的话把需求复述一遍，列出 PRD 没写清、需要产品确认的点。

→ 需求理解草稿
🤝 合流验收：三边完成后汇总——图有没有看全、关键主流程图主线亲自再核一遍、历史检索够不够。任何一边不达标，主线自己补做，绝不带着缺口往下走。
3
🧭 需求对齐
把 PRD 翻译成测试语言：目标是什么、入口在哪里、影响哪些端、配置/AB/接口/埋点有没有写清，没写清的先进入待确认。
读取 source/content.txt + source/tables.md + 图片转录结果 → 形成风险与待确认基础
4
🎯 定风险重点
先判断"这次改动最该测什么、最容易崩在哪"，定下优先级，不搞一碗水端平。
出例核心手册 authoring-core.md（一次读入，管到第 7 步）
5
🔍 逐维度防漏
拿出几十个测试维度的检查清单，一个个打勾：这维度测了 / 不涉及 / 待确认，不允许默默跳过。
§A 覆盖维度清单 · 涉及哪端才读对应的 code-risk-*.md 风险库
6
🧩 先树后例、原子出例
先把需求拆成多级分解树（数值逐项、分支逐行、结局逐个成节点——思维导图就由这棵树长出来），再给每个功能点挑测试方法（边界值 / 判定表 / 状态迁移…），最后写成一条条"一例一断言"的原子用例，禁止把多个数值/链路打包进一行期望。
§C 先树后例+原子用例硬规则 · §B 特征→方法决策表 → 产出 testcases.md
7
✅ 机器自检 质量校验
脚本自动检查用例结构、编号、必测维度是否齐全，还卡结构粒度：分组没细分、期望打包多断言、PRD 表格数值没落进用例（数值对账），都会被拦下打回重修。顺带把用例转成思维导图——树有多深图就有多深，无占位废层。
结构+粒度校验 validate_output.py（--tables 数值对账）· 转导图 md_to_mindmap.py → mindmap.puml
8
🚀 发布飞书 写飞书
自动在飞书新建一篇文档，排好版：需求理解 → 风险判断 → 思维导图 → 待确认 → 覆盖自检表。
发布规则 references/lark-output.md · 脚本 publish_to_lark_doc.py · 三块用例正文由思维导图承载，没有思维导图会拒绝发布（不发出不含用例的空文档）· 风险表「影响」列发布时自动改写为维度名（用例编号在文档里是死引用）· 中断可 --resume 断点续传不重复建档（直接重发会被护栏拦截），失败时保留本地交付与半成品 document_id
🎉
交付到手
拿到一个本地交付目录 + 一篇飞书文档。文档里的思维导图代码块，复制粘进飞书画板就是一张完整脑图。
为什么又快又不掉质量

快靠并行，稳靠四道闸

提速不是靠偷工减料，而是把没有先后依赖的活儿改成同时干；质量则由四条硬规则和机器校验兜底。

⚡ 快在哪
优化前
约 25–30 分钟
优化后
常规 15–20 分钟
看图、翻历史、读正文本来要排队一个个来，现在三线同时开工；大图也不再堆进主流程拖慢写作。图特别多、附件复杂或飞书网络抖动时会更久，但换来的是逐图转录级的信息保真。
🛡️ 稳在哪 · 质量四支柱
📥
保真读取文档/表格/图片全量抓取，内嵌电子表格（Sheet）实时读入；其余未解析块（多维表格/附件等）登记成"待确认"，不静默丢
📚
历史编译翻遍往期同类需求，踩过的坑、回归点必须接上并留检索证据
🔍
逐维过闸 + 粒度闸几十个维度逐个打勾；分组必须多级细分、期望必须原子断言、PRD 表格数值逐个对账——不合格机器校验直接报错
🧩
先树后例先落多级分解树（数值逐项/分支逐行/结局逐个）再定方法再写原子用例，导图由树长出；不写"验证功能正常"这种空话

飞书对接 · 常见误区

对接飞书靠自带脚本直连，不依赖外部 skill

同事常问"是不是用了那个飞书 skill？"——不是。读飞书、写飞书都是本流水线自己的 3 个脚本直连飞书接口完成的。

📥
read_doc.py读飞书：拉正文、表格、下载全部图片
📤
publish_to_lark_doc.py写飞书：新建文档、自动排版、回写记录
🔑
lark_common.py凭证与网络共享库，供上面两个调用
⚠️ 给同事的辨析：系统里那个 giggle:lark-docs 是通用飞书文档 skill，本链路没有用它。当前读写都由自带脚本直连，凭证链路更独立，减少 gateway/CF 登录状态对发布的影响。另一个 writing-lark-test-mindmaps 已完全弃用，不在链路内。看到它们别以为是本流水线的一部分。
投产前置与边界

能放心用，但边界要讲清楚

这条流水线已经能进入日常使用，但它不是黑盒发布系统。该人工复核的地方保留人工，该失败兜底的地方保留本地交付。

✅ 投产前置条件

  • Lark Developer 应用权限已开通并发布版本。
  • 默认 Drive 文件夹已给应用写入权限。
  • 本机或 VPN 能访问 config 服务与 Lark OpenAPI。
  • validate_output.py 校验通过后才允许发布飞书。

⚠️ 明确边界

  • 不自动回写 qa-knowledge-base，避免未验证信息污染知识库。
  • 不修改原 PRD，不覆盖历史飞书文档。
  • 不直接生成飞书原生画板，只提供 PlantUML 代码块。
  • 飞书发布失败时，本地文件仍是有效交付物；已建 docx 会返回 document_id 供排查。
  • 内嵌电子表格（Sheet）已能实时抓取（埋点表等）；多维表格（Bitable）、视频、附件仍需明确处理策略，用户要求跳过时登记风险并跳过。
